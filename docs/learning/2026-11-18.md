### Architecture

Current frontend data flow:

```text
Node.js API
  -> serviceApi.getServices()
  -> useServices()
  -> toServiceCard()
  -> ServiceHealthGrid
  -> ServiceHealthCard
```

The backend status values are `healthy | degraded | down`; the UI maps these to `Running | Degraded | Down`. This keeps backend domain values separate from presentation labels.

## React and TypeScript concepts practiced

### Rendering arrays

Use `.map()` to transform each data item into a React element. This makes the number of rendered cards data-driven rather than hardcoded. Use a stable identifier such as `service.id` as the React key.

### Separation of concerns

- API service: performs HTTP communication and handles the response.
- Custom hook: owns the React data-fetching lifecycle and async UI state.
- Transformation function: maps backend contracts into UI-specific data.
- Grid: lays out a collection of cards.
- Card: presents one service.

### API response types

The endpoint returns a response object with a `data` array and `meta` information. We discussed using a generic response wrapper such as:

```ts
interface ApiResponse<T> {
  data: T;
  meta: {
    count: number;
    generatedAt: string;
  };
}
```

A specialized response can then use `ApiResponse<ServiceSummary[]>`.

### Fetch and errors

- `fetch()` returns a Promise.
- HTTP 4xx/5xx responses do not automatically reject the Promise; check `response.ok`.
- Caught errors should be treated as `unknown` and narrowed before reading their message.
- A `Promise<ServicesResponse>` communicates that the API function resolves asynchronously to a typed response.

### Effects and cancellation

We discussed why fetching directly inside a component body is unsafe: rendering may happen repeatedly, which can start repeated requests.

The hook uses `useEffect` for the initial request and `AbortController` to cancel a fetch during cleanup. Intentional cancellation should not be displayed as an application error.

Cancellation only stops client-side request work where possible; it cannot guarantee that server-side work already started is undone.

### Loading, errors, and stale data

Desired UI behavior:
- Initial loading with no data: show a loading state.
- Initial failure with no data: show an error state.
- A later refresh failure with existing data: keep the last successful data visible and show a warning.
- A later successful refresh: replace old data, update the freshness timestamp, and clear the active warning.

We discussed separate concepts:
- Request timeout: bounds how long an individual request can take.
- Data freshness: measures how long since the last successful update.
- A stale dashboard does not by itself prove that the backend server is down.

### Retry strategy

Discussed exponential backoff and jitter to avoid continuously hitting a temporarily unhealthy service. Retry policy should depend on the failure:
- Do not automatically retry a malformed request (400).
- Do not blindly retry authentication errors (401).
- Usually do not retry a missing resource (404).
- Respect `Retry-After` for rate limiting (429).
- Consider bounded retries for transient server errors (500/503) and network failures.
- Retrying non-idempotent operations requires additional safeguards such as idempotency keys.

Automatic retries have **not yet been implemented** in the frontend hook.

## DSA practice — Two Sum

### Nested-loop approach

For each index `i`, check later indices beginning at `i + 1`. Starting at `i + 1` prevents pairing an element with itself and avoids checking each unordered pair twice.

- Worst-case time complexity: `O(n²)`.
- Auxiliary space complexity: `O(1)`.

### Map approach

Store previously seen numbers and their indices. For each number, calculate its complement and check whether that complement has already been seen.

- Expected time complexity: `O(n)`.
- Auxiliary space complexity: `O(n)`.

The Map approach trades additional memory for faster expected lookup. This is generally preferable for large inputs when memory is available, but algorithm choice should consider constraints.

The implementation discussed:

```ts
function twoSum(nums: number[], target: number): number[] {
  const map = new Map<number, number>();

  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];

    if (map.has(complement)) {
      return [map.get(complement)!, i];
    }

    map.set(nums[i], i);
  }

  return [];
}
```

The non-null assertion in `map.get(complement)!` is justified here by the preceding `map.has(complement)` check, though non-null assertions should generally be used sparingly.

Test cases to retain:
- `twoSum([2, 7, 11, 15], 9)` -> `[0, 1]`
- `twoSum([3, 2, 4], 6)` -> `[1, 2]`
- `twoSum([3, 3], 6)` -> `[0, 1]`
- `twoSum([1, 2, 3], 10)` -> `[]`

## Observability system-design concepts discussed

### Scaling service lists

- Use backend pagination to limit records and response sizes.
- Use frontend virtualization so only visible cards and a small surrounding range are rendered.
- For example: `GET /api/services?page=1&limit=50`.

### High-volume telemetry

If the pipeline receives more events than it can process:
- A queue can decouple ingestion from downstream processing and absorb short bursts.
- A queue is finite. If production persistently exceeds consumption, backlog grows and must be addressed.
- Monitor queue depth, message age, processing lag, and consumer capacity.
- Scale consumers when possible and define backpressure and overflow policies.
- Preserve critical outage/error events; aggregate or sample high-frequency measurements where appropriate.
- Batch updates before sending them to the browser rather than triggering a React render for every event.

### Aggregation correctness

An average alone can hide outliers. Useful aggregated signals include:
- Request count and rate.
- Error count and rate.
- Average latency.
- p50, p95, and p99 latency.
- Maximum latency.
- CPU and memory utilization.

Do not average per-server p95 values to calculate a fleet-wide p95. Use mergeable histogram buckets or sketches designed for distributed aggregation.

### Backpressure and UI update frequency

These terms solve related but different problems:
- Buffering temporarily holds incoming events.
- Batching groups events before processing or sending.
- Throttling caps how often an operation is run.
- Backpressure communicates that a consumer cannot keep up and asks producers or upstream stages to slow down or adapt.
- Virtualization limits the number of DOM elements rendered at once.

## Original answers and refined explanations

### Dynamic list rendering

**Original:**
> Map keeps it dynamic and renders as many cards as we have in our array

**Refined:**
> I use `.map()` to turn each service record into a React element. The number of rendered cards follows the input array, so I do not hardcode each card. Each item gets a stable key so React can identify it when the list changes.

### Separating API and presentation

**Original:**
> We should separate our concerns. The ServiceHealthCard is for displaying content. The api call can be in a hook for example what is just for the api call and pass the result to the ServiceHealthCard.

**Refined:**
> I separate data fetching from presentation. The API service handles HTTP communication, a custom hook manages asynchronous state and lifecycle, and presentational components receive typed data through props. This improves reusability, testability, and maintainability.

### Why use an Effect?

**Original:**
> it always would call the api also if we rerender.

**Refined:**
> Fetching is a side effect and should not run during rendering. A component can render many times, so initiating a request in its body can trigger repeated requests. I use an Effect to synchronize with the external API and define when the request should run.

### Why cancel a request?

**Original:**
> the useeffect still could run and process data. the cleanup function is a clear signal that the request is done and all data is processed.

**Clarification:**
The cleanup function does not mean that a request has completed. It runs before an Effect is restarted or when its component unmounts. An `AbortController` can cancel an in-flight fetch.

**Refined:**
> I use Effect cleanup to abort requests that are no longer needed. This avoids unnecessary client-side network work and helps prevent obsolete responses from updating the UI. I handle intentional cancellation separately from application errors.

### Choosing a Map for Two Sum

**Original:**
> Memory space is easy to add but we can not add time. I always would use map because it is O(n) and if we find matching we will return because we will look uo where did we see the number on which index and do not iterate again and again.

**Refined:**
> I would generally choose the Map approach because it reduces expected time complexity from O(n²) to O(n), at the cost of O(n) additional space. I store previously seen values and their indices, allowing expected constant-time complement lookup. I would still consider memory limits, input size, and constraints before choosing the approach.

### Paginating and virtualizing service cards

**Original:**
> i would introduce paginantion on the backend. the frontend I would start to introduce back pressure and buffer in badges and throttle.

**Refined:**
> I would paginate the service list on the backend and virtualize the frontend so only visible cards are rendered. For telemetry updates, I would batch and aggregate events, throttle UI updates, and apply backpressure when consumers cannot keep up with producers.

### Aggregating telemetry

**Original:**
> I would aggregate the updates with an avergae value. I still would keep the maximum value and throw an alert that we might sclae the system again if the ressources getting critical.

**Refined:**
> I would aggregate high-frequency telemetry but preserve request counts, averages, tail percentiles, maximums, and error rates so aggregation does not hide performance problems. I would alert on sustained resource saturation, increased latency, errors, or ingestion lag, and scale based on sustained demand rather than a single spike.

### Using a message queue

**Original:**
> i would push the events i can not handle in a message queue. I also would buffer the 30.000 event into bagdes and update the ui in a timly matter.

**Refined:**
> I would use a message queue to decouple ingestion from processing and absorb bursts, monitor queue depth and message age, and scale consumers where possible. I would aggregate and batch data for the dashboard instead of forwarding every individual event. I would also define backpressure, prioritization, and overflow policies because a queue cannot grow indefinitely.
